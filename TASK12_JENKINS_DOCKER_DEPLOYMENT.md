# Task 12: Jenkins-Docker Continuous Deployment

## Pipeline

`Jenkinsfile` enforces this order:

1. Check out the commit and prepare an image tag from the Maven version, Jenkins build number, and 12-character Git revision.
2. Compile, package, and run unit tests.
3. Run the Selenium/Failsafe integration-test quality gate.
4. Only after both test gates pass, build the Docker image and tag it with the unique build version and `latest`.
5. Authenticate to Docker Hub with a Jenkins credential and push both tags.
6. Pull the versioned image, replace the environment-specific container, verify `/api/health`, then verify Nginx and archive deployment evidence.

Example image tag:

```text
<dockerhub-namespace>/municipal-complaint-portal:1.0.0-SNAPSHOT-<build-number>-<commit>
```

The numbered/commit tag identifies the deployed build; `latest` is only a convenience tag. Deployment uses the versioned tag, not `latest`.

## Jenkins Configuration

- Use a Windows Jenkins agent with Git, JDK 17, Maven, Docker Desktop/Engine, PowerShell, and the existing Nginx installation available to the Jenkins service account. The pipeline uses `bat` and the deployment script configures the existing Nginx reverse proxy.
- Create a Docker Hub repository, then add a Jenkins **Username with password** credential with ID `dockerhub-credentials`. Use a Docker Hub access token as the password; do not place credentials in the repository or job parameters.
- Set the `DOCKERHUB_REPOSITORY` build parameter to the lowercase `namespace/repository` value for manual builds. For unattended webhook/SCM builds, configure the non-secret Jenkins global/node environment variable `DOCKERHUB_REPOSITORY_CONFIG` with that value so triggered builds do not depend on a manual parameter.
- Keep the environment-specific application and Nginx ports available on the deployment host.
- Configure the Jenkins job for this repository's `Jenkinsfile` and a commit/webhook or SCM-poll trigger. The runner needs permission to access the Docker daemon.

The pipeline stores Docker authentication in a build-specific workspace `DOCKER_CONFIG`, uses `--password-stdin`, logs out in the `post` block, and removes that temporary configuration after the run.

## Deployment and Evidence

`deploy/deploy.ps1` retains the earlier packaged-JAR deployment mode and adds a Docker mode for the Task 12 pipeline. In Docker mode it pulls the published tag before replacing the existing environment container. If the new container does not become healthy, it attempts to restart the previous image. The backend port is bound to loopback and Nginx remains in front of it.

On success, Jenkins archives `target/docker-deployment-evidence.json`. It records the versioned registry reference, local image ID, registry digest, container ID/status, and direct/proxied health responses. The Jenkins console also records both Docker Hub pushes. These are generated by a successful configured Jenkins run; no registry push or live deployment is claimed by this source-code change alone.

Useful post-build checks:

```powershell
docker image inspect <namespace>/municipal-complaint-portal:<version-tag>
docker ps --filter "name=municipal-portal-staging"
curl.exe http://localhost:8090/api/health
```

For an end-to-end demonstration, trigger the pipeline with `DOCKERHUB_REPOSITORY` set and retain the successful Jenkins run, archived JSON evidence, Docker Hub tag page, and health-check response.
